# Work Order Schema

The data the coordinator tracks for each maintenance request from intake through resolution. This is the recommended field set. Not every harness or PM software will support all of these. Use what's available, skip what isn't, and never block a work order because a non-critical field is missing.

## How to Use This File

When the coordinator creates or updates a work order, it should populate as many of these fields as it can from the information it has. Some fields come from the tenant during intake. Some come from the KB entry's "work order fields to capture" section. Some come from config. Some come from the vendor after dispatch.

If the harness or PM software has its own work order format, map these fields to that format as closely as possible. If a field doesn't exist in the target system, skip it. The coordinator should never fail because a field can't be stored.

## Fields

### Identification

- **work_order_id**: Unique identifier. Generated by the harness or PM software. If neither provides one, the coordinator should generate something reasonable (timestamp + unit, sequential number, whatever the harness supports).
- **status**: Current state of the work order. Common values: `new`, `triaging`, `troubleshooting`, `awaiting_dispatch`, `awaiting_approval`, `dispatched`, `scheduled`, `in_progress`, `completed`, `escalated`, `cancelled`. The coordinator updates this as the work order moves through the lifecycle.
- **created_at**: When the request was first received. ISO 8601 timestamp if the system supports it.
- **updated_at**: Last modification timestamp.
- **resolved_at**: When the issue was confirmed resolved (either by tenant during troubleshooting or after vendor completion and tenant confirmation).

### Property and Tenant

- **property_address**: Full street address of the property.
- **unit**: Unit number or identifier. Blank for single-family homes.
- **tenant_name**: Name of the reporting tenant.
- **tenant_phone**: Phone number for the tenant.
- **tenant_email**: Email if available.
- **tenant_preferred_contact**: How the tenant prefers to be reached (text, email, phone, portal). Defaults to however they submitted the request.
- **tenant_availability**: When the tenant is available for vendor access. Free text ("weekdays after 3pm", "anytime", "call first").
- **pets_in_unit**: Whether there are pets and what kind. Vendors need to know this.
- **access_instructions**: How to get into the property or unit (lockbox code, gate code, key location, tenant will be home). Pulled from config if available, confirmed with tenant if not.

### Issue Classification

- **category**: Top-level category (plumbing, electrical, hvac, appliances, general).
- **subcategory**: More specific (toilet, faucet, breaker, disposal, mold, lock, etc.).
- **kb_entry_id**: The KB entry used for triage, if one was matched (e.g., KB-PLUMB-002).
- **severity**: Severity classification level (critical, high, medium, low, cosmetic). From `references/decision-logic/severity-classification.md`.
- **habitability_issue**: Whether this is a habitability concern (true/false).
- **habitability_deadline**: If habitability, the response deadline based on jurisdiction lookup. ISO 8601 timestamp or relative description.
- **jurisdiction**: State (and city if relevant) for this property. Used for habitability window lookup.

### Issue Details

- **description**: Tenant's description of the problem in their own words.
- **intake_answers**: Key intake question responses. Free-form or structured, depending on what the harness supports. At minimum, capture whatever the KB entry's intake questions produced.
- **photos**: List of photo references (URLs, file paths, attachment IDs, whatever the system uses). Include a note for each: what it shows, when it was received.
- **videos**: Same as photos, for video.
- **diagnosis**: The coordinator's assessment after triage. What the issue likely is, what was tried, what the result was.

### Troubleshooting

- **troubleshooting_attempted**: Whether the coordinator attempted troubleshooting (true/false).
- **troubleshooting_level**: The aggressiveness level used (0-5, from config).
- **troubleshooting_steps**: What was tried, in order, and the result of each step. Useful for the vendor so they don't repeat what the tenant already did.
- **resolved_by_troubleshooting**: Whether troubleshooting fixed the issue (true/false).

### Responsibility

- **responsibility**: Who is responsible for the cost (owner, tenant, pending_review). From `references/decision-logic/tenant-responsibility-matrix.md` and company config.
- **responsibility_notes**: Why this classification was made. Especially important for grey areas or disputes.
- **tenant_informed_of_responsibility**: Whether the tenant was told about cost responsibility before dispatch (true/false). Required when responsibility is tenant.
- **responsibility_disputed**: Whether the tenant pushed back on the responsibility classification (true/false). If true, the PM needs to handle it.

### Vendor and Dispatch

- **vendor_name**: Name of the assigned vendor.
- **vendor_phone**: Vendor contact.
- **vendor_category**: Type of vendor dispatched (handyman, plumber, electrician, hvac, locksmith, pest_control, etc.).
- **dispatched_at**: When the vendor was dispatched.
- **scheduled_for**: The appointment window. Free text or structured (start time, end time), whatever the system supports.
- **vendor_arrived_at**: When the vendor arrived on-site, if tracked.
- **vendor_completed_at**: When the vendor finished, if tracked.
- **vendor_notes**: Vendor's report on what they found and what they did.

### Financial

- **nte_threshold**: The NTE that applied to this work order. From config.
- **estimated_cost**: What the coordinator estimated the repair would cost, if known before dispatch.
- **actual_cost**: What the vendor charged. Populated after completion.
- **approval_required**: Whether owner/PM approval was needed before dispatch (true/false).
- **approval_status**: pending, approved, denied, not_required.
- **approval_requested_at**: When the approval request was sent.
- **approval_received_at**: When approval was received.
- **approved_by**: Who approved it (name or role).

### Escalation

- **escalated**: Whether this work order was escalated to a human (true/false).
- **escalated_at**: When.
- **escalated_to**: Name or role of the person it was escalated to.
- **escalation_reason**: Why. Should match one of the triggers in `references/decision-logic/escalation-criteria.md`.
- **escalation_resolved**: Whether the escalation has been addressed (true/false).

### Follow-Up

- **follow_up_scheduled**: Whether a follow-up with the tenant is scheduled (true/false).
- **follow_up_at**: When the follow-up should happen.
- **follow_up_completed**: Whether follow-up was done (true/false).
- **tenant_confirmed_resolution**: Whether the tenant confirmed the issue is resolved (true/false).
- **recurrence_flag**: Whether this issue has occurred before at this unit (true/false). If true, note how many times and link to previous work orders if possible.

### Vendor Performance (If Tracked)

These are optional and only useful if the company wants to track vendor quality over time. Most PM software handles this separately.

- **vendor_on_time**: Whether the vendor arrived within the scheduled window (true/false).
- **vendor_first_visit_fix**: Whether the issue was resolved on the first visit (true/false).
- **tenant_satisfaction**: Tenant feedback on the repair, if collected. Free text or rating.

## What's Required vs. Nice to Have

The coordinator needs these to do its job on any work order:

- property_address (or some way to identify where)
- tenant_name and at least one contact method
- description (what's wrong)
- category and severity
- status

Everything else improves quality, documentation, and tracking, but the coordinator should never refuse to create a work order because optional fields are empty. Capture what you can, move forward.
